# Enterprise Knowledge Hub AI

Milestone 1: a vertical slice proving the core architecture — a mocked Google Drive
connector synced through a document pipeline (extract → chunk → embed) into a
permission-aware RAG chat that cites and can open the original source document.

Runs fully local: FastAPI + PostgreSQL + Qdrant + Redis/Celery + Ollama (local LLM)
+ sentence-transformers (local embeddings). No cloud AI APIs, no real OAuth yet —
the Google Drive connector is mocked behind the same interface a real one will use.

## Running locally

```
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

(`docker-compose.yml` alone is the hardened production shape -- see
[`docs/PRODUCTION.md`](docs/PRODUCTION.md); `docker-compose.dev.yml` layers
back bind mounts, `--reload`, and published debug ports for local iteration.)

- Frontend: http://localhost:5173
- Backend API: http://localhost:8010 (docs at /docs, health at /health)
- Qdrant dashboard: http://localhost:6333/dashboard
- Ollama: http://localhost:11434

## Getting an account

There's no seed data and no demo login -- create your own account:

1. Go to http://localhost:5173/signup and sign up (this also creates your workspace).
2. Verification emails aren't sent anywhere real in local dev; the console
   email provider just prints the message, so grab the verification link from
   the backend logs:
   ```
   docker compose logs backend | grep -A2 verify-email
   ```
3. Open that link (or paste the `token` query param into the verify-email
   flow in the UI) to verify, then log in and start chatting.

This needs no email credentials and no manual database access.

## Using Mistral instead of the local Ollama model

Set in `.env`:

```
AI_PROVIDER=mistral
MISTRAL_API_KEY=<your key from https://console.mistral.ai/>
MISTRAL_MODEL=mistral-small-latest   # or mistral-large-latest
```

Chat and RAG answers are then generated by the Mistral API instead of the
local Ollama container; embeddings stay local either way (AI_PROVIDER only
selects the LLM/chat model, not the embedding model).

## Connecting real Google Drive and Gmail

Both are "mock" connectors by default (fixture data, no external calls).
Switching either to "real" needs a Google Cloud OAuth client. The OAuth
client itself is one app-wide credential (created once, below); every
teammate who connects goes through their *own* Google consent and gets
their own connector account row, and everything anyone connects pools into
the same workspace-scoped, role-gated corpus everyone in that workspace can
query -- there's no per-user setup in Google Cloud, just this one client:

1. In [Google Cloud Console](https://console.cloud.google.com/), create or
   pick a project, then enable the **Google Drive API** and **Gmail API**
   under "APIs & Services -> Library".
2. Under "APIs & Services -> OAuth consent screen", configure an External
   consent screen and add the Google account(s) you'll connect with as test
   users (while the app is unverified).
3. Under "APIs & Services -> Credentials", create an **OAuth client ID** of
   type "Web application". Add this exact URI under "Authorized redirect
   URIs": the value of `GOOGLE_OAUTH_REDIRECT_URI` in `.env` (defaults to
   `http://localhost:8010/api/v1/connectors/google/oauth/callback`).
4. Copy the generated Client ID and Client Secret into `.env`:
   ```
   GOOGLE_OAUTH_CLIENT_ID=...
   GOOGLE_OAUTH_CLIENT_SECRET=...
   ```
5. Each teammate, with their own logged-in session (Bearer token), calls:
   - `GET /api/v1/connectors/google/oauth/start?connector_type=google_drive`
   - `GET /api/v1/connectors/google/oauth/start?connector_type=gmail`

   Each returns `{"authorization_url": "..."}` -- open that URL in a browser
   and approve access with *your own* Google account. Google redirects back
   to the callback endpoint, which creates/updates *that teammate's*
   connector account in "real" mode and immediately triggers a first sync
   for just their content. No frontend UI for this exists yet; the GET
   requests above (e.g. via `curl -H "Authorization: Bearer <token>"`) are
   the current way to trigger it.

Note on shipping this to real users (not just your own team running it
locally): the consent screen above is in Testing mode, which caps Google
logins to email addresses you've manually added as test users. Letting
arbitrary people connect requires submitting the OAuth consent screen for
Google's verification review (privacy policy, app homepage, and for Gmail
specifically often a security assessment) plus deploying at a real domain
and registering its callback URL as a second authorized redirect URI on the
same client.

Real-mode syncs pull read-only: Drive files (Docs/Sheets/Slides are
exported to text/CSV; other files downloaded as-is) and Gmail messages
(subject/from/date + plain-text body, `-in:chats -in:spam -in:trash`).
Attachments are not ingested yet.
